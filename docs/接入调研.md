### 雪球拦截页原文

> 请求异常已被安全策略拦截
> 如您本地未登录雪球账号，建议先 **登录** 后再访问重试。
> **如您本地有使用 AI Agent 等内容抓取工具，触发受限后会在最多几小时后自动解封，该类异常不接受提前解封申诉。**

雪球**明确点名 AI Agent**，而且是「触发即封、几小时自动解封、不接受申诉」的机制。

### 三道墙

1. **登录墙**：核心 API（自选股 / 关注动态 / 讨论区）全部要求 `xq_a_token` Cookie，未登录直接 400
2. **WAF JS 挑战**：部分接口返回 `_waf_*` 加密数据，必须由浏览器执行 JS 解出来，**纯后端 curl 拿不到明文**
3. **IP 黑名单**：请求频率一高就 `Seek IP Blacklisted`，自动解封要几小时，且不接申诉

### 如果要做，唯一可行的路子

**WebView2 内嵌雪球**，而不是后端代理：

```
DeskHost 里开一个隐藏 WebView2 → 加载 xueqiu.com（用户手动登录一次）
        ↓
页面内 JS 调 /v4/... 接口（自动带 Cookie，WAF 挑战由浏览器自动过）
        ↓
取到 JSON → postMessage 回卡片渲染
```

原因：WAF 的 JS 挑战**只能在真实的浏览器执行环境里过**，Node 后端做不到。

### 代价与风险

| 项 | 说明 |
|---|---|
| 登录 | 必须用户手动扫码/手机号登录一次，Cookie 存本地 |
| 频率 | 得压到很低（估计 5–10 分钟一次），否则触发封禁 |
| 稳定性 | 雪球随时可能改规则；封了只能等几小时 |
| 工作量 | 比小宇宙大，因为要处理隐藏 WebView + 登录态 + WAF |
| 封号风险 | 雪球明确反抓取，**有账号受限风险** |

### 建议

- **不推荐**像小宇宙那样做深度集成
- 如果一定要，退而求其次：**只做「快捷跳转」**，点卡片用浏览器打开雪球自选页，零风险
- 或者：**用雪球官方 App 的通知**，不在工作台里重复做

### 待用户拍板

问用户：是否能接受「手动登录 + 低频 + 有封号风险」这三条。

### 用户澄清的关键点

> 「webview 只是个接入窗口容器，我在上面该怎么登录怎么登录，你只是做了一个某个板块功能的壳而已，他这样都要封 IP？」

| 对比 | 我的探测 | WebView2 里的用户 |
|---|---|---|
| Cookie | 无 | 有（登录后） |
| UA | curl | 真实 Edge |
| 节奏 | 几百毫秒一个 | 鼠标本身 |
| 鼠标轨迹 | 无 | 有 |
| 雪球判定 | 爬虫 | 真人 |

### 用户第二条要求

> 「根本不需要考虑频率的问题，你也不用帮我自动刷新，所有的刷新动作都由我自己来操作。」

**所以最终方案：全程零定时器。** 只有用户点「刷新」才发一次请求。

### 已落地的架构

```
┌─ DeskHost（桌面贴，WebView2 #1，UserData=wv2data）
│    └─ 工作台页面 → 雪球卡片
│          │ chrome.webview.postMessage({type:'xueqiuFetch', path, reqId})
│          ▼
│    C# OnWebMessage → HandleXueqiuFetch()
│          │ ExecuteScriptAsync(fetch(...))
│          ▼
└─ XueqiuWindow（普通窗口，WebView2 #2，UserData=wv2data_xueqiu）
      └─ 真实 xueqiu.com，用户在这里登录、浏览
      └─ fetch 结果 → PostWebMessageAsJson 回投主页面
```

**为什么两个 UserDataFolder 要分开**：WebView2 同一个 UserDataFolder 不能被两个进程/环境同时占用。分开还能保证雪球登录态跟工作台隔离。

### Bug 记录：200 响应被误判成「要求登录」

**现象**：自选股请求 `ok:true status:200`，数据完整回来了，卡片却显示「雪球要求登录」。

**原因**：

```js
if (r1.status === 401 || /请重新登录|error_code/.test(t1)) {
  throw { needLogin: true, ... };
}
```

`t1` 是响应体原文。雪球股票数据里本来就有 `error_code` 这类字段，
正则一匹配就抛错，**200 的成功响应被打成需要登录**。

**修法**：状态码优先，只在 401/403 时才判定需要登录；非 200 直接报 HTTP 错误。

```js
if (r1.status === 401 || r1.status === 403) throw { needLogin: true, ... };
if (r1.status !== 200) throw new Error('列表 HTTP ' + r1.status);
```

**教训**：别拿响应体里的字符串做状态判断，先看 HTTP 状态码。

**注意**：切换会改变雪球窗口当前显示的页面（卡片抓哪个 tab，窗口就停在哪个），这是刻意的 —— 用户能对上。

### 消息正文：展开键 + 拿全文（2026-11-13 22:28）

**用户反馈**：关注和热门里的每条消息看不全。

**原因有两层**：

1. **雪球页面自己折叠长文** —— DOM 里只有前几行，`.timeline__unfold__control` 是它的「展开」按钮。
   不点它，抓到的文本本来就只有 100~150 字。
2. **卡片这边也有截断** —— 渲染时 `slice(0, 160)`，CSS 还 `-webkit-line-clamp: 4`。

**修法**：

- **抓取端**：`ClickTabAndGrab` 里先点开雪球所有 `.timeline__unfold__control`，等 700ms 再抓；
  文本上限从 300/400 放宽到 **3000** 字。
- **渲染端**：去掉 `slice(0,160)`，正文超 90 字给一个「展开全文」按钮，
  点一下 `.xq-post-x` 加 `.open` 类，`-webkit-line-clamp` 变 `unset`。

**实测文本长度**（同一批 6 条）：

```
[147, 154, 369, 164, 186, 598]
```

之前全是 147 左右，现在 369 / 598 的长文都能拿到全文。

**展开键**：6 条全有，点击后按钮文字 展开全文 ↔ 收起，`clamp: 4 → none`。

**注意**：抓取总耗时变成 2500ms（等 tab 切换）+ 700ms（等展开）= 约 3.2 秒，
前端 `ask()` 的超时是 26 秒，够用。
